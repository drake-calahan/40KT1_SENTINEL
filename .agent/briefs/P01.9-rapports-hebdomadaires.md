# Brief `P01.9` — Rapports hebdomadaires : conformité (`D3`) et vulnérabilités (`D4`)

- **Agent** : `cursor` (skill `coder`) · **Statut** : **en attente de `P01.1`**
- **Ce que `P01.1` apporte** : un agent qui produit réellement des données de
  conformité et un inventaire de paquets. Avant, il n'y a rien à lire.
- **Branche** : `cursor/p01-9-rapports-hebdomadaires`
- **Zone de fichiers** : `scripts/`, `responder/` **interdit**
- **Relecture obligatoire** : `claude`

## Pourquoi ce lot existe

`D3` et `D4` ont été répondues : conformité de durcissement **en lecture seule**,
rapport hebdomadaire, **aucune remédiation automatique** · inventaire de
vulnérabilités des paquets, rapport hebdomadaire, **pas d'alerte temps réel**.

Deux rapports, donc, et pas deux alertes. C'est un choix d'exploitation adossé à
`F5` — 5 min par jour, 1 h de repassage par semaine : un flux de vulnérabilités
en temps réel serait lu deux semaines puis coupé.

## Périmètre — ce qu'il faut produire

### 1. Deux scripts Python, dans `scripts/`

`rapport_conformite.py` et `rapport_vulnerabilites.py`. Même forme, mêmes règles :

- **Lecture seule.** Aucune remédiation, aucune mise à jour de paquet, aucun
  changement de configuration. `D3` et `D4` sont explicites, et `unattended-
  upgrades` appartient à HQ : Sentinelle **signale** un retard, elle ne met rien
  à jour.
- **Trois états, pas deux.** Chaque contrôle rend `ok`, `ko` ou **`unknown`**.
  Une source illisible, un service muet, une commande absente → `unknown`, et le
  rapport le dit en toutes lettres. *Un contrôle qui réussit sans avoir regardé a
  déjà coûté deux incidents dans HQ.*
- **Sortie sur la sortie standard**, en Markdown court, plus un code de retour :
  `0` rapport produit · `1` rapport impossible à produire · **jamais** un rapport
  vide rendu `0`.
- **Aucun envoi.** Le câblage de l'alerte est `P02.0`, et il n'existe pas encore.
  Un rapport qui s'envoie tout seul dans un dépôt où l'alerte n'est pas prouvée
  est exactement le défaut que ce dépôt corrige.
- Type hints partout, `ruff` (lint + format), `pytest`.

### 2. Deux unités systemd, **livrées désarmées**

`sentinel-rapport-conformite.service` + `.timer`, idem pour les vulnérabilités.
Préfixe `sentinel-*` obligatoire — les unités `40kt1-*` appartiennent à HQ.

Les fichiers d'unité sont **posés** ; ni activés, ni démarrés. Le timer s'arme
par un runbook, jamais par un merge. Le cadencement proposé : une fois par
semaine, hors de la fenêtre de sauvegarde de 03:30.

### 3. Les tests

`pytest`, et la moitié des cas porte sur ce qui **ne marche pas** :

- source de données absente → `unknown`, pas `ok`, et code de retour non nul ;
- source présente mais illisible (droits) → `unknown` ;
- source vide → `unknown` et **pas** « zéro vulnérabilité » ;
- source nominale → rapport avec le bon décompte.

Le quatrième cas est le seul qui teste le succès. C'est voulu : *« zéro
vulnérabilité »* affiché parce qu'on n'a rien pu lire est le pire résultat
possible de ce lot.

## Hors périmètre — ne pas toucher

- `responder/` — zone fermée jusqu'à la vague 5.
- Tout envoi Discord / ntfy (`P02.0`).
- Toute remédiation, y compris « évidente ».
- Toute activation d'unité ou de timer.

## Critères d'acceptation

1. `ruff check` et `ruff format --check` verts sur `scripts/`.
2. `pytest` vert, avec les quatre cas ci-dessus, dont **trois de dégradation**.
3. Aucun script n'écrit hors de son fichier de sortie ; aucun n'appelle une
   commande de modification.
4. Les quatre unités existent, aucune n'est activée, aucune n'est démarrée, et
   toutes sont préfixées `sentinel-`.
5. Aucun `*_enabled` passé à `true` — la garde CI de `P00.8` le vérifie.
6. Un `unknown` est visible dans la sortie d'exemple collée dans la PR.

## Preuves à coller dans la PR

```bash
ruff check . && ruff format --check .
```

```bash
python -m pytest -q
```

La sortie d'un rapport joué **sans** source de données, montrant les `unknown` et
le code de retour :

```bash
python scripts/rapport_vulnerabilites.py; echo "code=$?"
```
