## La règle qui gouverne ce lot

**On prouve d'abord qu'une alerte arrive, on arme ensuite.** Dans cet ordre, et
pas un autre. Un dispositif armé sans destinataire est exactement le défaut que
ce dépôt existe pour corriger — c'est la règle n° 1 de [`RULES.md`](../RULES.md),
et elle vient d'un incident réel de HQ.

Conséquence directe sur le périmètre : **ce lot ne livre pas une alerte, il livre
un chemin d'alerte et sa preuve.** Rien ne s'abonne à ce chemin dans cette PR.

## Périmètre — ce qu'il faut produire

### 1. `scripts/sentinel-notify.sh` — un wrapper mince

Il appelle `notify.sh` **de HQ**, tel quel : `F1` a tranché — même mécanisme,
destinations distinctes. On ne recopie pas le pousseur, on l'appelle. Une copie
divergerait, et c'est le jour où elle diverge qu'on en a besoin.

- Les destinataires viennent du `.env` **de Sentinelle** :
  `SENTINEL_DISCORD_WEBHOOK_URL` (salon `#securite`) et `SENTINEL_PUSH_URLS`.
  **Jamais** les variables de HQ : deux destinations, une seule mécanique.
- Le chemin du pousseur vient de `hq_notify_script` (`group_vars`), pas d'un
  chemin en dur : il diffère entre les deux nœuds.
- Sous-commande `test-alert` : envoie un message d'essai identifiable, avec le
  nom du nœud et l'horodatage.
- **Codes de retour, et c'est le cœur du lot** :
  `0` message accepté par les deux canaux · `1` échec d'envoi ·
  **`2` configuration absente**. `2` n'est **pas** `0` : un chemin non configuré
  qui rend `0` reproduit la sauvegarde offsite muette du retex du 04/09 — elle
  existait, elle était configurée, elle n'écrivait rien, et personne ne le
  savait.
- Un envoi partiel (Discord accepté, push refusé) rend `1` et **dit lequel**.
- Chaque envoi est journalisé localement : date, canal, sévérité, verdict.
- `#!/usr/bin/env bash`, `set -euo pipefail`, `shellcheck` propre, commentaires
  en français, **aucun secret en clair dans une sortie ou un journal**.

### 2. Le runbook de preuve

Dans `docs/runbooks/mise-en-service.md`, la section qui décrit **le geste du PO** :

1. poser les deux valeurs dans le `.env` de Sentinelle du nœud ;
2. jouer `sentinel-notify.sh test-alert` ;
3. **constater l'arrivée sur le téléphone** — pas dans un journal, sur le
   téléphone ;
4. constater l'arrivée dans `#securite` ;
5. seulement alors, consigner le câblage comme prouvé dans `ACTIVE.md`
   § « Ce qui est armé » — geste réservé au PO.

Le runbook dit aussi ce qu'on fait quand ça ne marche pas : code `2` = valeur
absente, code `1` = destinataire refusé, et dans les deux cas **on ne passe pas à
la suite**.

## Hors périmètre — ne pas toucher

- `sentinel_alerting_enabled` reste `false`. Le script existe, rien ne l'appelle.
- La grille de sévérité (`P02.1`) et l'agrégation (`P02.2`, `claude`).
- `notify.sh` lui-même : il appartient à HQ, on ne le modifie pas.
- Toute valeur de webhook ou de sujet ntfy dans le dépôt. Le `.env.example` porte
  déjà les **noms** ; il ne portera jamais les valeurs.

## Critères d'acceptation

1. `shellcheck` propre.
2. Les trois codes de retour sont démontrés, sortie collée : configuration
   absente → `2` ; destinataire invalide → `1` ; nominal → `0`.
3. Aucun secret n'apparaît dans le journal ni dans une sortie.
4. Le script ne modifie rien d'autre que son propre journal.
5. Le runbook décrit le geste du PO, dans l'ordre, avec le cas d'échec.
6. Aucun `*_enabled` passé à `true`.
