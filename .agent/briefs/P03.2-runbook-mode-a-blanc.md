# Brief `P03.2` — Runbook du mode à blanc

- **Agent** : `cursor` (skill `tech-writer`) · **Statut** : **esquisse**
- **Pourquoi esquisse** : le mode à blanc se documente à partir du **journal réel**
  de l'exécuteur — son format, ses motifs de refus, ce qu'on y lit le matin.
  Ce format est fixé par `P03.0` (`claude`). Écrire le runbook avant, c'est
  documenter un journal imaginaire.
- **Devient `prêt` quand** : `P03.1` est livré et le format du journal est figé.
- **Branche** : `cursor/p03-2-runbook-mode-a-blanc`
- **Zone de fichiers** : `docs/runbooks/`

## Intention

Deux semaines pendant lesquelles l'exécuteur journalise ce qu'il **aurait** fait,
sans rien faire. Le runbook dit : comment on vérifie qu'il est bien à blanc,
comment on lit son journal en 5 minutes par jour, ce qui constitue un geste
**injustifié**, et ce qu'on fait quand on en trouve un.

Le critère de sortie de la phase 3 est *« zéro geste à blanc jugé injustifié sur
la période »* : le runbook doit rendre ce jugement possible sans relire du code.

## Ce que le lot devra porter

- La vérification que le mode à blanc est **effectivement** actif — pas la
  variable qu'on croit avoir posée, l'état constaté sur la machine.
- La lecture quotidienne : où, quoi chercher, combien de temps.
- La lecture des **refus** autant que des gestes. *Au matin, on doit pouvoir lire
  ce que la machine a fait sans nous — et ce qu'elle n'a pas fait.*
- La conduite à tenir sur un geste injustifié : ce qui se corrige dans une règle,
  ce qui se corrige dans le catalogue (et donc par amendement d'`ADR-002`).
- Le lien avec le journal des faux positifs de `P01.7` : même discipline, deux
  périodes.
