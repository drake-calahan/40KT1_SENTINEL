# Brief `P00.8` — Garde CI « rien n'est armé »

- **Agent** : `cursor` · **Statut** : **prêt**
- **Branche** : `cursor/p00-8-garde-armement`
- **Bloqué par** : `P00.6`
- **Zone de fichiers** : `.github/`
- **Taille attendue** : un script, un workflow, deux lignes de documentation.

## Pourquoi ce lot existe

Le gabarit de PR porte déjà la case : *« Aucun `*_enabled` passé à `true` — cette
PR n'arme rien »*. Une case cochée par celui qui livre est une **déclaration**.
La règle n° 1 du dépôt — *tout est désarmé par défaut, armer est un geste
d'exploitation* — mérite mieux qu'une déclaration : elle mérite un contrôle qui
échoue.

C'est exactement le raisonnement d'`ADR-003` sur le bornage `cgroup` : *« ce qui
rend la condition vérifiable plutôt que déclarative »*.

Et le mode de panne visé est réel : un rôle Ansible qui pose
`sentinel_response_enabled: true` dans ses `defaults` arme la réponse automatique
sur deux machines de production **au merge**, sans qu'aucun runbook ne soit joué,
et sans que rien dans la PR ne le crie.

## Périmètre — ce qu'il faut produire

### 1. `.github/scripts/garde-armement.sh`

Un script autonome, **exécutable en local** — c'est ce qui le rend testable et
donc digne de confiance. Interface :

```bash
.github/scripts/garde-armement.sh <ref-de-base>
```

Il lit les **lignes ajoutées** du diff `git diff <ref-de-base>...HEAD` et échoue
si l'une d'elles arme quelque chose.

**Les motifs refusés** (sur une ligne ajoutée, insensible aux espaces autour du
séparateur) :

| Motif | Ce qu'il attrape |
|---|---|
| `sentinel_[a-z_]*_enabled:\s*true` | une variable d'armement Ansible passée à `true` |
| `SENTINEL_[A-Z_]*_ENABLED\s*=\s*true` | la même chose dans un `.env` ou un shell |
| `sentinel_response_dry_run:\s*false` | la sortie du mode à blanc, qui **est** un armement |
| `SENTINEL_RESPONSE_DRY_RUN\s*=\s*false` | idem |

**Les chemins exclus**, et le motif de chaque exclusion :

| Chemin | Pourquoi |
|---|---|
| `docs/**`, `**/*.md`, `.agent/**` | un runbook doit pouvoir **montrer** la commande d'armement ; c'est sa raison d'être |
| `.github/scripts/garde-armement.sh` | le script contient ses propres motifs |
| `.github/workflows/armement-guard.yml` | idem |

**Le message d'échec** est en français, cite le **fichier**, le **numéro de
ligne** et la ligne elle-même, et se termine par la phrase qui dit quoi faire :

> Armer est un geste d'exploitation, décrit par un runbook et joué par un humain
> (`.agent/RULES.md` § 1). Si ce lot doit livrer du code d'armement, la valeur
> reste `false` dans le dépôt et le runbook porte le geste.

**Codes de retour** : `0` rien trouvé · `1` au moins un motif trouvé · `2`
impossible de calculer le diff (base introuvable, dépôt superficiel). **`2` n'est
pas `0`** : un contrôle qui n'a pas pu regarder ne rend jamais vert — c'est le
faux vert de [`DISCOVERY.md`](../DISCOVERY.md), déjà payé deux fois par HQ.

Contraintes shell : `#!/usr/bin/env bash`, `set -euo pipefail`, aucune dépendance
hors `git`, `grep`, `sed`. Commentaires en français.

### 2. `.github/workflows/armement-guard.yml`

- Déclencheur : `pull_request` **uniquement** (le contrôle porte sur un diff ;
  sur `push` vers `main` il n'a pas de base naturelle). **Pas** de `paths` : un
  filtre de chemins ferait passer sans contrôle exactement les PR qui touchent
  autre chose que `infra/`.
- `permissions: contents: read`.
- `concurrency` sur `${{ github.workflow }}-${{ github.ref }}`, comme les trois
  workflows existants.
- `actions/checkout@v4` avec `fetch-depth: 0` — sans quoi la base n'est pas dans
  le clone et le script rend `2`.
- Une seule étape utile : `.github/scripts/garde-armement.sh "origin/${{ github.base_ref }}"`.
- L'en-tête du fichier explique **en français** ce que le job garantit et ce
  qu'il ne garantit pas : il voit les valeurs littérales, pas une variable
  d'inventaire calculée ni un `-e` passé à la main. Ce n'est pas un dispositif
  de sécurité, c'est un garde-fou de relecture.

### 3. Deux lignes de documentation

- `.github/pull_request_template.md` : la case existante devient
  *« Aucun `*_enabled` passé à `true` — **vérifié par la CI `garde-armement`** »*.
- `.cursor/PLAYBOOK.md`, checklist « session propre » : même mention sur la ligne
  correspondante.

## Hors périmètre — ne pas toucher

- Les trois workflows existants.
- Toute tentative d'analyser sémantiquement du YAML Ansible (résolution de
  variables, `when`, templates). Le lot livre un contrôle **textuel** sur des
  lignes ajoutées, et le dit.
- Toute règle qui ferait échouer la CI sur du texte documentaire.

## Contraintes

- Versions d'actions épinglées comme dans les workflows existants.
- Aucun secret, aucun appel réseau, aucune permission d'écriture.
- Le script doit être **relançable en local** par le PO, sans GitHub.

## Critères d'acceptation

1. Sur une branche propre, `garde-armement.sh origin/main` rend `0`.
2. Sur une branche contenant une ligne ajoutée
   `sentinel_response_enabled: true` dans `infra/ansible/`, il rend `1` et nomme
   le fichier et la ligne.
3. La **même ligne** ajoutée dans `docs/runbooks/armement-de-la-reponse.md` rend
   `0` — un runbook a le droit de montrer le geste.
4. Avec une base introuvable (`garde-armement.sh origin/inexistante`), il rend
   `2` avec un message explicite, et **jamais** `0`.
5. Le workflow apparaît sur la PR du lot et il est vert.

## Preuves à coller dans la PR

Les quatre cas ci-dessus, avec la commande **et** sa sortie, y compris le code de
retour :

```bash
.github/scripts/garde-armement.sh origin/main; echo "code=$?"
```

Fabriquer les cas 2 et 3 sur un commit temporaire local, montrer la sortie, puis
le retirer de la branche livrée. La PR livrée ne contient **aucun** de ces
commits d'essai.
